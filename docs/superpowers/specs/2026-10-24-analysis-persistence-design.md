# Первый пакет: сохранность проверяемого анализа

Статус: принят к реализации 24 октября 2026 года. Задача [#76](https://github.com/VsevolodCod/EVIA/issues/76).
Основание: [конкурентный анализ и аудит](../../competitive-review-2026-10-24.md).

## Пользовательский результат

После вопроса к данным пользователь может закрыть страницу, вернуться в чат и
увидеть тот же текст, SQL, таблицу, время и сведения об источнике. При открытии
в другом браузере источник восстанавливается по серверным данным.

## Границы первого пакета

Сохраняем структурированный ответ и привязку источника. Строим основу будущих
карточек. Авторизация, HTTP-идемпотентность, бизнес-словарь и редактор дашбордов
остаются отдельными пакетами с собственными проверками.

## Данные и совместимость

- Добавить в серверное сообщение ассистента необязательный версионированный
  payload результата: валидированный `AgentResponse`, связанный с message_id.
  Сохранять ограниченный результат, который уже разрешён API; не полные CSV.
- Добавить к чату необязательный source_id для текущего одноисточникового UI.
  Первый запрос нового чата закрепляет источник; попытка продолжить его с другим
  возвращает понятный конфликт, без вызова LLM. Самостоятельный `/agent/ask`
  сохраняет существующий контракт.
- Привязка источника относится к чату; snapshot_id и версия схемы относятся
  к конкретному результату. Обновление CSV не переписывает прошлое вычисление.
- Старый чат с неизвестным источником остаётся доступен для чтения; продолжение
  требует явного выбора источника. Не доверять одному localStorage для миграции.
- Миграция существующей SQLite добавляет nullable-поля без удаления записей;
  запуск на пустой и существующей БД должен быть идемпотентным.

## Запись и чтение

- В одной короткой транзакции сохранять сообщение ассистента и его payload.
  Вызов LLM не удерживает блокировку SQLite.
- В GET истории возвращать payload только связанного сообщения. LLM получает
  текст истории через существующий путь; JSON результата не добавляется в prompt
  автоматически и не увеличивает его размер незаметно.
- API сохраняет совместимость с текстовыми сообщениями. Неизвестная версия
  payload не интерпретируется как новый успешный расчёт.
- Ошибочный ответ не сохранять как успешный аналитический артефакт.
  Существующий сценарий восстановления незавершённого вопроса должен работать.

## Интерфейс

- Восстанавливать `analysis`, `results`, `tool_results`, `answer_kind` и `timing`
  из серверного payload. Использовать существующие компоненты результатов.
- У старых текстовых ответов явно показывать отсутствие сохранённых деталей;
  не генерировать их заново при открытии истории.
- При исчезновении источника разрешать просмотр сохранённого результата,
  а новый расчёт блокировать с понятным сообщением.
- При наличии серверной привязки использовать её вместо localStorage. Кэш
  браузера не определяет источник и не считается контролем доступа.

## Обязательная проверка

1. Реальный HTTP-сценарий с временной БД: вопрос → ответ → закрытие клиента →
   чтение истории; структурированный результат совпадает с исходным.
2. Перезапуск backend сохраняет SQL, таблицу, snapshot_id и timing.
3. Очистка localStorage не теряет серверную привязку источника.
4. Старый формат SQLite мигрирует без потери сообщений; повторный запуск безопасен.
5. Новый snapshot не изменяет сохранённый ответ; исчезнувший источник не ломает чтение.
6. Вопрос с другим source_id отклоняется до вызова LLM.
7. Текстовая старая история, ошибка модели и пагинация остаются рабочими.
8. Приёмка в браузере: результаты доступны после перезагрузки, на desktop и mobile.

## Последовательность выпуска

Сначала регрессионный тест подтверждённой потери результата, затем миграция и API,
затем восстановление UI и проверки совместимости. Перед production — резервная
копия SQLite и прогон миграции на копии. Изменения готовятся отдельной веткой;
не включать в неё посторонний локальный коммит о benchmark.
