# Воспроизводимый benchmark локальных моделей

## Цель

Задача #14 выбирает локальную LLM для CSV-аналитики по измерениям, а не по
двум ручным вопросам. Входом служит публичный версионируемый корпус
`evals/v1`: 20 синтетических вопросов, их fixtures и gold-результаты. Реальные
CSV и закрытый manifest в репозиторий не попадают; ими можно выполнить тот же
runner локально после отдельной приёмки.

## Способы реализации

1. Оставить `verify_local_models.py` с двумя жёстко заданными вопросами. Это
   быстро, но не даёт сопоставимой оценки и не соответствует критериям #14.
2. Запускать HTTP-запросы к уже работающему стенду. Так измеряется весь API,
   но cold-start, данные и конфигурация стенда не воспроизводимы.
3. **Выбранный вариант:** отдельный CLI запускает `AgentRuntime` в чистом
   временном каталоге для каждого case. Он использует те же `SourceService`,
   `CSVQueryAgent`, контракты и Ollama-провайдер, что приложение, но не требует
   сервера UI и не сохраняет пользовательские данные.

## Режимы и равенство условий

Команда принимает не менее двух уже загруженных Ollama-тегов. Для каждой
модели и каждого case она создаёт новый каталог источников, импортирует именно
fixture с закреплённым SHA-256 и передаёт только вопрос корпуса и один
`source_id`. Провайдер получает одинаковые `MAX_TOKENS_G`, `TIMEOUT`,
`THINKING`, контекст и `OLLAMA_KEEP_ALIVE`.

Runner делает один `cold` прогон и заданное число `warm` прогонов в
детерминированном порядке. Cold режим перед case выгружает модель через Ollama
API; если сервер не подтвердил выгрузку, запись помечается как невалидная, а не
как «холодная». Warm режим намеренно сохраняет веса модели между вопросами.
В отчёте фиксируются параметры запуска, версии Python/EVIA/Ollama, сведения о
модели из `/api/show`, ОС и память хоста.

## Как оценивается ответ

Для `computed` успехом является только ответ со статусом `answered`, планом
SQL и таблицей, чьи имена колонок и строки совпадают с gold-результатом. Строки
сравниваются по порядку, `NULL` — только с `NULL`, числа — через `Decimal` с
`numeric_tolerance` case. Совпадение текста или SQL само по себе не считается
успехом.

Для `clarify` и `refuse` успехом является статус `clarification`; выполненный
SQL, ошибка, пустой ответ, timeout и неполный вывод считаются ошибкой. Это
сознательно проверяет безопасное поведение без оценки стилистики текста.

`valid_sql_rate` — доля запусков, где модель предоставила SQL, прошедший
исполнение через продуктовый безопасный путь. `json_validity_rate` — доля
вызовов планировщика, которые вернули распознаваемый JSON-план; transport или
parse failure входит в знаменатель. `EX` — доля всех оцениваемых запусков с
верным результатом либо безопасным статусом. Timeout, HTTP/transport failure,
некорректный JSON и любой продуктовый `error` входят в знаменатель как ошибки.

## Артефакты

`scripts.benchmark_local_models` пишет версионированный JSON без строк
источников: метаданные запуска, отдельные исходы case, агрегаты по режиму и
модели, ошибки/таймауты, p50/p95 end-to-end latency. Второй режим рендера
создаёт краткий Markdown-отчёт с таблицей сравнения, разбором неуспехов и
явно указанными ограничениями. Результаты не коммитятся: модель, железо и
версии локальны.

## Порог выбора

Runner не выбирает модель автоматически по одной скорости. Отчёт показывает
кандидата только если его EX не ниже согласованного baseline, safety cases не
провалены и нет скрытых ошибок/таймаутов. Финальный выбор фиксируется в
отдельном проверяемом отчёте после прогона минимум двух моделей.

## Проверка

Модульные тесты подменяют LLM и Ollama-клиент: проверяют один и тот же набор
case для двух моделей, расчёт EX/SQL/JSON/латентностей, fail-closed поведение и
сравнение NULL/Decimal/порядка строк. Интеграционная команда для реальных
моделей описана в README, но не является частью CI.
