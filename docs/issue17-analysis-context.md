# #17: продолжение выполненного анализа

Изменение построено поверх PR #118 и общего цикла инструментов из #117.
Удалённые планировщики CSV/дашборда не возвращаются.

## Контракт

`AgentResponse.analysis_contexts` содержит до восьми `CalculationContext` версии 1:
source/snapshot/schema_version, result_id, выполненный SQL, агрегаты, условия,
группировки и представление table/bar/line. Эти поля извлекает сервер после
успешного query_data. Текст ответа модели не становится источником параметров.

Контекст сохраняется в существующем versioned analysis_payload сообщения.
Новая таблица, миграция БД и глобальная память процесса не требуются.
После restart его читает новый AgentRuntime из серверной истории конкретного чата.

`continue_analysis` создаётся в отдельном реестре на каждый запрос. Его изменения:

- `result_id` выбирает один из нескольких прошлых расчётов. При единственном
  результате выбор можно опустить. Неоднозначный выбор ничего не вычисляет.
- `group_by` меняет разрезы; пустой список убирает их. `time_field` + `time_grain`
  добавляют календарный интервал day/week/month/quarter/year, сохраняя показатель
  и условия. Временное поле должно иметь тип даты.
- `add_filters` добавляет AND-условия; `remove_filter_indexes` удаляет только явно
  выбранные прежние условия. Индексы соответствуют списку filters в контексте.
  Например, смена года удаляет две границы периода и добавляет новые, оставляя
  сегмент. `date_part=month`, operator=ne, value=7 исключает июль.
- `measure_field` + `aggregate` явно заменяют показатель. Агрегат выбирается из
  count/sum/avg/min/max; SUM/AVG проверяют числовой тип поля.
- `presentation` меняет вид. Если меняется только вид и архивный QueryResult
  доступен, SQL не запускается повторно: сохраняются result_id, строки и provenance.
  В ответе есть `reused_result`; UI открывает нужный вид и сохраняет CSV-экспорт.

Новый самостоятельный вопрос может использовать query_data: успешные запросы
текущего вопроса становятся новым активным набором расчётов.

## Версии и изоляция

До передачи истории проверяются source/snapshot/schema_version. Устаревшие или
чужие параметры не передаются модели и дают clarification без inference.
Сообщение со статусом stale — граница сброса: следующий вопрос может начать
анализ актуальной схемы, старый контекст и предшествующий текст больше не используются.
При пересчёте дополнительно сверяется provenance, чтобы не смешать импорт,
произошедший во время выполнения, с прежними условиями.

Контекст не хранится в полях общего AgentRuntime или общего ToolRegistry.
Существующая привязка source_id к chat_id и HTTP 409 при смене источника сохраняются.

## Бюджет и границы

В prompt передаются максимум 12 последних текстовых сообщений, до 2000 символов
каждое и до 12000 символов суммарно. Расчётный контекст отдельно ограничен
16000 символами; строки результата в него не копируются. Это символьные бюджеты,
не обещание фиксированного числа токенов для разных моделей.

Условия продолжаются через SQL AST, после чего запрос проходит существующий
read-only guard и лимиты SourceService. Автоматическое редактирование доступно
для простого SELECT одного источника без JOIN/CTE/subquery/window/HAVING/DISTINCT.
Для сложного запроса возвращается уточнение: инструмент не упрощает его молча.
При новой группировке строки упорядочиваются по разрезам, прежний SQL LIMIT
сохраняется. Отсутствующие периоды не заполняются нулями.

Контекст фиксирует выполненное выражение, а не утверждает, что бизнес-определение
метрики согласовано: версионируемый semantic catalog относится к #19.
Продолжение редакции уже сохранённых dashboard_id относится к #28/#29.

## Проверка

CI проверяет цепочку реальных HTTP/SQLite/DuckDB расчётов:
125 для A за 2025 → по месяцам 30/40/55 → столбцы без SQL → исключение июля 30/40.
Между шагами открывается новый ChatManager. Проверяется сохранённый payload.
Отдельные сценарии: явная смена года и показателя, длинная история, параллельные
источники одного runtime, stale/reset, неоднозначный result_id и неверные изменения.
Frontend проверяет запрошенный вид и экспорт результата продолжения.

Выбор инструментов в этих тестах делает scripted LLM. Это проверяет контракты,
числа и сохранение, но не заменяет живую последовательность с реальной моделью
на Railway. Модель всё ещё может выбрать новый query_data вместо продолжения;
качество этого выбора необходимо проверить на опубликованной сборке. До живой
приёмки и независимого ревью полное закрытие #17 не подтверждено.

Локально приложение, Ollama и тяжёлые тесты не запускаются. Полные проверки — CI.
