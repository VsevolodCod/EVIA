# Проверка гипотез в Linza-BI

## Назначение

Модуль `app/hypothesis` проверяет аналитические гипотезы по подключённым
источникам данных. Запрос содержит формулировку гипотезы и список
конкретных проверок. Тип проверки выбирается по полю `method`.

Поддерживаются два метода:

-   `compare` --- сравнение агрегированной метрики в двух группах;
-   `relationship` --- оценка корреляционной связи между двумя
    агрегированными метриками.

Численные результаты вычисляются реализациями проверок по данным.
Языковая модель может подготовить формулировку и параметры проверки, но
не должна подменять выполнение вычислений предположениями.

## Структура модуля

-   `models.py` --- Pydantic-модели запроса, метрик, фильтров и
    проверок.
-   `base.py` --- общие SQL-утилиты: обработка идентификаторов и
    значений, сборка фильтров, извлечение строк.
-   `engine.py` --- валидация запроса, выбор реализации по `method`,
    запуск проверок и формирование общего результата.
-   `implementations/compare.py` --- сравнение двух групп.
-   `implementations/relationship.py` --- корреляционный анализ.
-   `implementations/__init__.py` --- регистрация доступных реализаций.

## Процесс выполнения

1.  Формируется `HypothesisRequest`: `statement` и массив `checks`.
2.  Pydantic проверяет структуру запроса и допустимые значения полей.
3.  `HypothesisEngine` выбирает реализацию по `method`.
4.  Реализация применяет фильтры и получает агрегированные данные через
    SQL.
5.  `compare` рассчитывает различие между группами; `relationship`
    оценивает корреляцию между парами агрегатов.
6.  Результаты объединяются в `HypothesisResult`. Ошибки следует
    интерпретировать как ошибки выполнения, а не как опровержение
    гипотезы.

## Формат запроса

Пример для метода `compare`:

``` json
{
  "statement": "Средний чек после изменения процесса вырос",
  "checks": [
    {
      "method": "compare",
      "id": "before-after",
      "description": "Сравнить средний чек до и после изменения",
      "metric": {
        "source_id": "sales_source",
        "aggregation": "avg",
        "field": "amount"
      },
      "left": {
        "filters": [
          {"field": "period", "operator": "eq", "value": "before"}
        ]
      },
      "right": {
        "filters": [
          {"field": "period", "operator": "eq", "value": "after"}
        ]
      },
      "expected": "increase"
    }
  ]
}
```

Имена источника и полей в примере условные. Для реального запроса они
должны соответствовать доступной схеме данных.

### `statement`

Текстовое описание гипотезы. Оно задаёт смысл анализа, но само по себе
не меняет алгоритм вычисления.

### `checks`

Список независимых проверок. Запрос должен содержать от 1 до 20
проверок. Тип проверки определяется полем `method`.

Несколько проверок позволяют разложить сложное предположение на
отдельные измеримые части. Успешное выполнение вычисления ещё не
означает, что гипотеза подтверждена.

## Принципы интерпретации

-   **Результат должен опираться на данные.** Не следует придумывать
    численные значения на основании текста гипотезы.
-   **Корреляция не доказывает причинность.** Связь между показателями
    не означает, что один показатель вызывает изменение другого.
-   **Качество данных влияет на вывод.** Пропуски, малое число
    наблюдений, типы столбцов и способ группировки могут повлиять на
    результат.
-   **Фильтры определяют выборку.** Вывод относится только к строкам,
    удовлетворяющим заданным условиям.
-   **Ошибка вычисления не равна отрицательному результату.** Нужно
    отдельно рассматривать статус выполнения и содержательный вывод.

Подробные параметры методов, фильтров и интерпретация статистики
приведены в [hypothesis_methods.md](hypothesis_methods.md).

## Добавление нового метода

1.  Описать входные параметры в `models.py`.
2.  Добавить новый тип в дискриминируемое объединение по полю `method`.
3.  Реализовать класс проверки с общим интерфейсом исполнения.
4.  Зарегистрировать реализацию в `implementations/__init__.py`.
5.  Добавить тесты для валидации, SQL, вычислений, граничных случаев и
    изоляции ошибок.
6.  Обновить `hypothesis_methods.md`.

При работе с SQL нужно безопасно обрабатывать имена полей и значения
фильтров. Нельзя собирать SQL напрямую из непроверенного
пользовательского текста.
