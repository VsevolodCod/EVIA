# #16 — сохранение постоянных чатов

Это отчёт об исходном исправлении #16. Последующее сохранение полного ответа
и привязка источника описаны в [сохранённом результате анализа](analysis-history.md).

Дефект подтверждён на базе `a27cefe`/интеграции: `get_or_create()` возвращал `ChatHistoryResponse` вместо `Chat`; второй `/agent/chat` завершался 400 из-за отсутствия `updated_at`. Страница последних 50 сообщений также использовалась как полная история для последующей перезаписи. Регрессионный прогон до исправления: 5 ошибок из 6 тестов.

## Реализация

`app/chat_repository.py` отделяет полную доменную модель от HTTP-страницы истории. Прежний импорт `app.chat_manager.ChatManager` сохранён. Чтение полного чата возвращает `Chat(temporary=False)` и все сообщения. Запись дописывает новые `message_id` после текущей максимальной позиции, существующие сообщения неизменяемы. Повтор `save()` того же снимка идемпотентен. Устаревший или частичный снимок не удаляет сообщения другой операции.

SQLite `BEGIN IMMEDIATE` резервирует writer до чтения позиций. Транзакция короткая, LLM вызывается снаружи. Ограничения уникальности остаются в БД; ошибка полностью откатывает новые сообщения и metadata. Это не `asyncio.Lock` одного процесса: конкурентные менеджеры на независимых соединениях используют одну блокировку SQLite. Схема БД не меняется, копирование и удаление имеющихся диалогов не требуется.

Временные чаты хранятся только в памяти менеджера, чтение и запись используют отдельные копии, несохранённые изменения не попадают в историю. После перезапуска они недоступны. Постоянная история доступна после открытия нового engine.

## HTTP и совместимость

`POST /agent/chat` и `AskResponse.chat_id` сохраняют форму. Вопрос сохраняется **до** LLM: при сбое модели он остаётся целым пользовательским сообщением, выдуманный assistant-ответ не добавляется. Это предыдущее поведение API, а не атомарность всей пары вопрос/ответ. HTTP-повтор без ключа идемпотентности может создать ещё один вопрос; защита UI от повторов и согласованный request ID относятся к #18/#4. Идемпотентность `save(message_id)` не выдаётся за идемпотентность HTTP.

`GET /chats/{id}?limit=50` возвращает последние сообщения в хронологическом порядке. Для следующей старой страницы используйте `before=<next_before>`. Курсор — исключающая верхняя позиция; новые сообщения справа не сдвигают диапазон. `next_before=null` и `has_more=false` обозначают начало истории. `before=0` возвращает пустую страницу. Отрицательные параметры отклоняются; одновременные ненулевой offset и before дают 400.

Прежние `offset` и `next_offset` сохранены для совместимости. Они отсчитываются от конца и стабильны только без новых записей; новый UI должен использовать before. Заголовок, count и страница читаются из одного SQLite snapshot. Список чатов сортируется по updated_at и chat_id для разрешения совпадающего времени.

## Проверки и границы

`python -m pytest tests/test_chat_persistence.py -q` проверяет first/second ask, 80+ сообщений, restart, идемпотентное сохранение, 12 одновременных записей через два engine, два HTTP-запроса, курсор во время добавления сообщения, rollback всех записей/metadata, temporary mode, частичный устаревший снимок, запрет изменения сообщения, повторный create и delete.

Не реализованы семантическая память, сжатие контекста LLM, UI-сессии (#18), сохранение tool_results в истории, авторизация или несколько независимых пользователей. Все вопросы длинной истории передаются агенту; управление контекстным окном — отдельная задача. Пагинация истории работает без загрузки ORM relationship целиком; продолжение диалога намеренно читает всю историю, чтобы не терять её при сохранении.
