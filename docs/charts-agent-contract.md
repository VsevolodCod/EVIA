# DashboardCardsV1

Этот документ описывает типы карточек `DashboardSpecV1`, их поля, правила вычисления и отображения.

Все карточки имеют общие поля:

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `id` | string | Да | Уникальный идентификатор карточки в пределах дашборда. |
| `type` | string | Да | Тип карточки. |
| `title` | string | Да | Заголовок карточки. |
| `description` | string | Нет | Краткое пояснение. |
| `filters` | Filter[] | Нет | Дополнительные фильтры карточки. |

`id` используется для сопоставления спецификации и результата вычислений. Повторяющиеся ID в одном дашборде недопустимы.

Каждая ссылка на поле содержит `source_id` и `field`. Backend проверяет существование поля и доступ к источнику. Для межтабличных вычислений требуется поддержка связей на стороне backend; произвольные объединения не допускаются.

Общие правила агрегации, фильтров, форматирования и сортировки определяются `DashboardSpecV1`.

## 1. KPI — ключевой показатель

`type: "kpi"`

Показывает одно агрегированное значение: выручку, количество заказов, среднюю цену или другой показатель.

Пример спецификации:

```json
{
  "id": "total_revenue",
  "type": "kpi",
  "title": "Выручка",
  "field": {
    "source_id": "sales_source",
    "field": "revenue"
  },
  "aggregate": "sum",
  "format": {
    "type": "number",
    "decimals": 0
  },
  "filters": []
}
```

Поля:

- `field` — источник и поле, используемые при вычислении;
- `aggregate` — обязательная операция агрегации;
- `format` — формат отображения результата;
- `filters` — необязательные условия, ограничивающие набор данных.

Backend вычисляет KPI самостоятельно. Спецификация не должна содержать готовое числовое значение в качестве источника истины.

`count` возвращает количество строк после применения фильтров. `sum`, `avg`, `min` и `max` применяются к выбранному полю с проверкой совместимости типов.

Результат карточки содержит `value`, `format` и статус вычисления. Если данных нет, backend должен отличать пустой набор от числового нуля. Отображение пустого результата определяется клиентом.

## 2. Line — линейный график

`type: "line"`

Используется для временных рядов и последовательностей значений.

`x.time_grain` задаёт календарную группировку: `day`, `week`, `month`, `quarter`,
`year` или `null` (исходные значения). Ненулевой шаг требует `x.type=temporal`
и типизированного поля даты/времени. Группировка использует начало полного
интервала с годом, неделя начинается в понедельник. Период ограничивается
отдельными фильтрами и не выводится из шага. Условия сохраняются вместе с
карточкой, включая переданные через дополнительный аргумент `build_chart.filters`.
Пример плана и правила отказа: [#29 — условия дашборда](issue29-dashboard-constraints.md).

Пример спецификации:

```json
{
  "id": "monthly_revenue",
  "type": "line",
  "title": "Выручка по месяцам",
  "x": {
    "source_id": "sales_source",
    "field": "month",
    "type": "temporal",
    "label": "Месяц",
    "sort": "asc"
  },
  "y": {
    "source_id": "sales_source",
    "field": "revenue",
    "aggregate": "sum",
    "label": "Выручка",
    "format": {
      "type": "number",
      "decimals": 0
    }
  },
  "series": null,
  "filters": [],
  "limit": 100
}
```

Поля:

- `x` — поле группировки по горизонтальной оси;
- `x.type` — тип значения: `temporal`, `category` или `number`;
- `x.sort` — порядок точек;
- `y` — числовой показатель и агрегат;
- `series` — необязательное поле группировки на отдельные линии;
- `limit` — максимальное число точек;
- `filters` — условия отбора данных.

Backend группирует записи по X и, если задано `series`, по значению серии. Для каждой группы вычисляется Y.

Для временных рядов сортировка по времени должна выполняться по фактическому значению, а не по форматированной подписи. Дублирующиеся значения X объединяются только согласно заданному агрегату.

В будущем может быть добавлено поле `time_granularity` со значениями `day`, `week`, `month`, `quarter`, `year`. Оно определяет группировку дат, но не меняет исходные значения в источнике.

Отсутствующие периоды не должны автоматически интерпретироваться как нулевые значения. Если требуется непрерывная временная шкала, политика заполнения пропусков должна задаваться отдельно.

## 3. Bar — столбчатая диаграмма

`type: "bar"`

Используется для сравнения категорий: выручка по регионам, число заказов по статусам, количество пользователей по тарифам.

Пример спецификации:

```json
{
  "id": "revenue_by_category",
  "type": "bar",
  "title": "Выручка по категориям",
  "x": {
    "source_id": "sales_source",
    "field": "category",
    "type": "category",
    "label": "Категория",
    "sort": "desc"
  },
  "y": {
    "source_id": "sales_source",
    "field": "revenue",
    "aggregate": "sum",
    "label": "Выручка",
    "format": {
      "type": "number",
      "decimals": 0
    }
  },
  "series": null,
  "orientation": "vertical",
  "filters": [],
  "limit": 10
}
```

Поля `x`, `y`, `series`, `filters` и `limit` работают аналогично линейному графику.

`orientation` задаёт ориентацию столбцов:

- `vertical` — вертикальные столбцы;
- `horizontal` — горизонтальные столбцы.

Для категорий рекомендуется сортировка по агрегированному значению по убыванию. Если категорий больше `limit`, backend возвращает только выбранные категории. Объединение оставшихся в «Прочее» должно быть отдельной явно поддерживаемой возможностью, а не неявным поведением.

При наличии `series` диаграмма может показывать несколько значений на категорию. Режим группировки или накопления серий в дальнейшем можно задать отдельным полем.

## 4. Pie — круговая диаграмма

`type: "pie"`

Используется для отображения долей категорий в составе целого.

Пример спецификации:

```json
{
  "id": "revenue_share",
  "type": "pie",
  "title": "Доля выручки по категориям",
  "x": {
    "source_id": "sales_source",
    "field": "category",
    "type": "category",
    "label": "Категория",
    "sort": "desc"
  },
  "y": {
    "source_id": "sales_source",
    "field": "revenue",
    "aggregate": "sum",
    "label": "Выручка",
    "format": {
      "type": "number",
      "decimals": 0
    }
  },
  "filters": [],
  "limit": 8
}
```

`x` определяет сектора, `y` — их значения. Backend агрегирует данные по категориям.

Значения должны быть неотрицательными. Если сумма значений равна нулю, диаграмму долей построить нельзя. Нулевые значения могут быть скрыты клиентом.

`limit` ограничивает количество секторов. Если требуется категория «Прочее», backend должен явно поддерживать её формирование после группировки и сортировки. Модель не должна самостоятельно добавлять фиктивные категории или значения.

Для круговой диаграммы не используется поле `series`: несколько независимых серий обычно делают доли неоднозначными. Для сравнения распределений лучше использовать другой тип визуализации.

## 5. Scatter — диаграмма рассеяния

`type: "scatter"`

Используется для исследования зависимости двух числовых величин, например цены и количества продаж.

Пример спецификации:

```json
{
  "id": "price_quantity",
  "type": "scatter",
  "title": "Цена и количество продаж",
  "x": {
    "source_id": "sales_source",
    "field": "price",
    "type": "number",
    "label": "Цена"
  },
  "y": {
    "source_id": "sales_source",
    "field": "quantity",
    "type": "number",
    "label": "Количество"
  },
  "series": {
    "source_id": "sales_source",
    "field": "category",
    "label": "Категория"
  },
  "filters": [],
  "limit": 1000
}
```

Поля:

- `x` — числовое поле по горизонтальной оси;
- `y` — числовое поле по вертикальной оси;
- `series` — необязательная категория для различения точек по цвету;
- `limit` — максимальное количество точек;
- `filters` — условия отбора данных.

В отличие от `line` и `bar`, базовый режим `scatter` показывает отдельные записи без агрегации. Поэтому `aggregate` не требуется.

Если необходима агрегация, она должна быть явно определена в будущей версии контракта: например, как группировка по двум измерениям. Backend не должен самостоятельно суммировать точки или менять их смысл.

Поскольку количество строк может быть большим, лимит для `scatter` должен быть ограниченным. Если данных больше лимита, backend должен применять документированную стратегию отбора или возвращать признак усечения данных.

## 6. Area — график с областями

`type: "area"`

Используется для отображения изменения объёмов во времени, в том числе нескольких серий.

Базовая структура совпадает с `line`: `x`, `y`, `series`, `filters`, `limit`.

Дополнительно предусматривается:

- `stacking: "none"` — независимые области;
- `stacking: "stacked"` — накопительные области.

Для накопительного графика следует проверить, что значения имеют смысл для сложения. Если серии описывают разные единицы измерения, их нельзя складывать в одну область.

`area` можно включить в расширение контракта после реализации базовых типов.

## 7. Table — табличная карточка

`type: "table"`

Используется для отображения конкретных записей или результатов группировки, когда график не подходит.

Пример спецификации:

```json
{
  "id": "top_sales",
  "type": "table",
  "title": "Крупнейшие продажи",
  "source_id": "sales_source",
  "columns": [
    {
      "field": "category",
      "label": "Категория"
    },
    {
      "field": "revenue",
      "label": "Выручка",
      "format": {
        "type": "number",
        "decimals": 2
      }
    }
  ],
  "filters": [],
  "sort": [
    {
      "field": "revenue",
      "direction": "desc"
    }
  ],
  "limit": 100
}
```

Поля:

- `source_id` — источник таблицы;
- `columns` — список разрешённых полей для отображения;
- `filters` — условия отбора строк;
- `sort` — список правил сортировки;
- `limit` — максимальное количество строк.

В табличной карточке каждое поле должно проверяться по схеме источника. Форматирование влияет только на отображение.

Пагинация может быть реализована на уровне результата backend. Нельзя передавать в спецификации произвольные SQL-выражения вместо имён полей.

## Результаты вычислений

Спецификация карточки описывает требуемую операцию, а не её результат.

Backend должен возвращать результат с тем же `id`, типом карточки, статусом вычисления и данными соответствующего формата.

Для KPI возвращается одно значение `value`. Для `line`, `bar`, `pie` и `area` — набор агрегированных точек. Для `scatter` — набор пар координат и, при необходимости, меток серий. Для `table` — строки и описание колонок.

Если вычисление карточки завершилось ошибкой, результат должен содержать безопасный код ошибки и не должен выдавать фиктивные значения вместо фактических данных.

## Совместимость и развитие

Набор поддерживаемых типов и полей определяется версией контракта и возможностями backend. Наличие описания типа в документации не означает, что его реализация уже доступна.

Неизвестные типы карточек, агрегаты, фильтры и поля отклоняются. Если ошибка локализована в одной карточке, остальные корректные карточки могут быть возвращены независимо.

Новые типы и параметры добавляются с учётом обратной совместимости. Изменения семантики существующих полей требуют новой версии контракта.
