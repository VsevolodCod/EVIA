## 2. Что предложено в документации капитана, но ещё не сделано

[PR #101](https://github.com/VsevolodCod/EVIA/pull/101) предлагает ясную модель продукта: **данные → один первичный отчёт → исследование в чате → явное добавление результата → сохранение, повторное открытие и PDF**. Обычный вопрос не изменяет отчёт; «добавь это» закрепляет конкретный результат; «создай дашборд» пополняет текущий отчёт, отдельный создаётся по явной просьбе. Это хороший ориентир для визуальной иерархии, но не описание работающего `main`. PR имеет статус draft и прямо просит командное согласование до слияния.

Целевые сущности `Analysis`, единый `Artifact`, версия/ревизия отчёта, отмена изменения, привязка ответа к конкретной карточке, повторное открытие без LLM/SQL и экспорт выбранной сохранённой ревизии пока отсутствуют как сквозной пользовательский путь. Текущий обзор из `frontend/src/features/analytics/Dashboard.tsx` нельзя выдавать за этот отчёт.

В спецификации есть требование автономной локальной поставки. Текущая целевая проверка #74/#75 ведётся на Railway с Cloud.ru; решение о локальной поставке нужно принять отдельно, оно не превращается в реализованную функцию от изменения дизайна.

## 3. Что сделал Саша и почему PR #102 пока не часть продукта

В `agent_tools/plots@5a354d0` появились backend-маршруты `GET /dashboards/ids`, `/dashboards/{id}`, `/dashboards/{id}/build`, `/charts/{id}`, `/charts/{id}/build`; параметр `dashboard_id` добавлен в запросы агента и чата. Есть инструменты `build_chart`, `compose_dashboard`, добавления/удаления карточек и получения определения. Ветку можно использовать как основу для интеграции **после исправления**.

Однако PR имеет конфликты с `main` в 11 файлах и его [отдельно запущенный CI `40426326177`](https://github.com/VsevolodCod/EVIA/actions/runs/40426326177) остановился при сборе backend-тестов: отсутствуют импортируемые `DashboardSpec` и `app.csv_query_agent`. Новых тестов для маршрутов/цикла дашборда в PR нет. Ветка удаляет `CSVQueryAgent` и `DashboardQueryAgent` и направляет выбранный источник через общий цикл инструментов; перед слиянием требуется проверить, что быстрые ответы, SQL, уточнения и исправление из #100 не потеряны. Строка `Closes #26/#28/#29` в описании PR пока не равна приёмке этих задач.

Самое важное для фронтенда: PR #102 **не меняет `frontend/`**. Текущий `frontend/src/api.ts` не описывает новые маршруты, `App.tsx` отправляет чат без `dashboard_id`, а `GeneratedDashboard` принимает только старый результат инструмента `create_dashboard` с `version: 1` и карточками `kpi`/`line`. Новые инструменты ветки называются `build_chart` и `compose_dashboard`; их результат автоматически этим компонентом не отображается. В `AgentRuntime` ID приложенного дашборда пока добавляется текстом в prompt; это ещё не проверенный механизм выбора активного отчёта или его ревизии.

**Вывод для сегодняшнего UI:** нельзя рисовать работающую галерею, «Добавить в отчёт», редактирование карточек или отправку ID дашборда как уже подключённые действия. Подготовить место и состояния можно, а активировать — после backend-контракта и сквозной проверки.

## 4. Карта экранов и точные названия на сегодня

1. **Слева — «Источники» и «История диалогов».** Выбор источника меняет контекст данных; выбор диалога открывает его ответы. Кнопка «Новый анализ» сейчас лишь сбрасывает состояние UI/открывает загрузку (`App.tsx`), серверный анализ не создаётся. Пока назвать её «Новый источник» или «Начать с CSV» и отдельно дать «Новый диалог», если это действие доступно.
2. **В центре — «Обзор источника» / «Данные» / «Результат вопроса».** В `SourceInspector.tsx` уже есть вкладки «Обзор», «Столбцы», «Качество», «Данные», «Схема», «Результат». Объединить «Столбцы» и «Схема» в одну понятную вкладку с режимом подробностей; «Качество» оставить отдельным. «Результат» показывать при выборе конкретного вопроса, не как второй отчёт.
3. **Справа — «Чат EVIA».** Ответ, таблица/график и объяснение расчёта принадлежат одному сообщению. `AnalysisResult.tsx` повторяет ответ в центре, который уже виден в чате; оставить один основной текст ответа, а в центре показывать только крупную таблицу/график по выбранному сообщению с ссылкой «К ответу».
4. **На мобильном — те же три контекста:** «Источники/Данные», «Результат», «Чат». Смена вкладки не должна сбрасывать источник или диалог. Крупный маскот и плавающие элементы не должны закрывать графики, поле ввода и ошибки.

Сырой JSON `ToolResults.tsx`, UUID, SQL и время выполнения полезны для диагностики, но в обычном ответе должны жить под «Как получен результат» / «Технические детали». Ошибку инструмента показывать человеческим текстом и следующим действием; успешный результат не маркировать ошибкой из-за технического вложения.

## 5. Порядок сегодняшней работы над интерфейсом

### P0 — сделать честным и понятным существующий путь

1. **Сверстать одну иерархию.** Источник → обзор данных → вопрос → конкретный результат. Переименовать обещающие больше функции слова «анализ», «отчёт», «дашборд» там, где сейчас только обзор/предпросмотр. Удалить визуальное впечатление, что центральный обзор автоматически редактируется через чат.
2. **Развести точные и выборочные данные.** У общего количества строк/точных полей указать «весь источник»; у частот, распределений, графиков и CSV обзора — «по первым N строкам» или фактическое покрытие. Не смешивать выборочный график и точный KPI без подписи. Если нет пригодного поля, показывать спокойное пустое состояние, а не бессмысленную диаграмму.
3. **Упростить результат вопроса.** Один ответ, одна таблица или визуализация, понятные фильтры/источник/число строк. Кнопка CSV только там, где есть табличные строки, с предупреждением об ограничении. Подробности инструментов раскрывать по запросу. Убрать дубли ответа и декоративные карточки, которые повторяют те же данные.
4. **Привести действия к реальному эффекту.** «Сохранить PDF» заменить на «Печать / сохранить PDF» до готового экспорта отчёта; обзорный CSV подписать «Скачать строки предпросмотра». Для CSV обзора также применить защиту от формул из `features/results/csvExport.ts` перед тем, как считать действие безопасным. Не показывать «Добавить в отчёт» как активную кнопку, пока нет сквозного сохранения.
5. **Закрыть состояния интерфейса.** Загрузка, источник без строк, ошибка профиля, ошибка модели, неполный ответ, пустой результат SQL, долгий ответ и повтор. Ошибка должна сохранять введённый вопрос и не создавать лишний диалог/дашборд. Проверить узкий экран и доступность клавиатурой.

### P1 — сразу после исправления и приёмки PR #102

6. Согласовать с backend точные JSON-контракты и ownership дашборда. Добавить типизированные вызовы списка/получения/построения и явную обработку `404`, пустого списка, частично неуспешного построения.
7. Показать галерею сохранённых дашбордов и открытие конкретного по ID; один и тот же объект должен пережить обновление страницы. Отправлять `dashboard_id` только при явном выборе пользователем и показывать, к какому дашборду относится команда. Отдельно проверить, что чат-команда действительно меняет выбранный объект, а не только передаёт ID модели текстом.
8. Использовать общий рендерер для результата `build_chart`/`compose_dashboard` и открытого дашборда. Пересчитать и проверить квартальные суммы по исходным данным; не переименовывать месячные точки в кварталы. Повтор команды и сбой не должны создавать дубли.

### P2 — после согласования продуктового PR #101

9. Реализовать серверную единицу «Анализ», один основной отчёт, явное закрепление результата, ревизии/отмену и контекст ссылок «это»/«вторая карточка». Только после этого вводить в навигацию названия «Анализы» и «Отчёт» без оговорок.
10. Сохранить результат и происхождение каждого блока для открытия без нового inference; печатать выбранную ревизию с источниками, фильтрами, единицами и охватом. Затем принимать #28–#31 и демонстрационный сценарий.

### Отложить до устойчивого базового пути

ClickHouse, продвинутые причинные/прогнозные сценарии, большие редакторы палитр и сложные автоматические рекомендации не должны занимать главный экран раньше P0/P1. В GitHub это отдельный backlog; не маскировать их под уже работающие возможности.

## 6. Короткая проверка для каждого нового макета

- Пользователь с пустым аккаунтом понимает, как загрузить CSV и где увидеть ошибки импорта.
- На обзоре ясно, какой источник/версия выбраны и какие числа полные, а какие получены из предпросмотра.
- Вопрос в чате даёт один понятный ответ; таблица, график и расчётные детали относятся к нему же.
- Пустой ответ, лимит генерации и недоступность модели выглядят по-разному и позволяют повторить запрос.
- Нельзя случайно принять обзор источника или чат-превью за сохранённый отчёт.
- На мобильном доступны источник, ответ, действия и поле ввода без перекрытий.
- Макет не требует от `main` API, которого там нет; элементы будущего этапа либо отсутствуют, либо явно помечены прототипом.
