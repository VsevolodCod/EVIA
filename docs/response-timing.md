# Время ответа и локальная оптимизация

Таймер в чате измеряет фактическое ожидание с помощью монотонного `performance.now()`. Пока запрос выполняется, показано «Ожидание … с»; после успешного ответа — «Ответ за … с». Ошибка и отмена останавливают счётчик; повтор начинает новый замер. Время хранится вместе с ответом в истории своего источника. Это не процент готовности и не прогноз. Счётчик не объявляется экранным диктором каждые полсекунды.

В `/agent/ask` и `/agent/chat` добавлено необязательное поле `timing`:

| Поле | Значение |
| --- | --- |
| `elapsed_ms` | Весь вызов `AgentRuntime.ask`, включая сериализацию контекста |
| `llm_ms` | Сумма длительностей обращений к LLM-провайдеру, включая HTTP и ожидание Ollama |
| `tools_ms` | Сумма времени выполнения инструментов |
| `calls[]` | Измерения каждого завершённого обращения к модели |
| `calls[].elapsed_ms` | Длительность обращения, измеренная backend |
| `calls[].model` | Имя модели из ответа провайдера, если доступно |
| `calls[].load_ms` | Время загрузки модели по данным Ollama |
| `calls[].prompt_ms` | Обработка входных токенов по данным Ollama |
| `calls[].generation_ms` | Генерация токенов по данным Ollama |
| `calls[].prompt_tokens`, `generated_tokens` | Счётчики токенов провайдера |

Ollama возвращает длительности в наносекундах; адаптер переводит их в миллисекунды ([официальный API](https://docs.ollama.com/api/chat)). Недоступные значения остаются `null`, а не выдуманным нулём. Для mock/OpenAI доступны измерения длительности обращения, но специфические метрики Ollama отсутствуют. Скорость генерации считается как `generated_tokens / generation_seconds`; нулевой знаменатель не отображается.

Браузерное время дополнительно включает сеть и получение/декодирование ответа. Серверный `elapsed_ms` не включает сохранение чата до/после агента, сериализацию HTTP-ответа и сеть. Метрики вызова Ollama и его внутренних этапов могут отличаться из-за очереди и накладных расходов; их нельзя складывать между собой. API пока не передаёт поток токенов, поэтому **время до первого токена не измеряется**. При исключении агент пишет длительности в `agent_timing outcome=error`; UI показывает время до ошибки, без выдуманных внутренних метрик. В эти строки логов не добавляются вопросы, ответы или строки CSV.

Старые клиенты могут игнорировать `timing`; новый UI принимает ответы без него. Обновлены JSON Schema и fixtures контракта v1. Это совместимое добавление, формат `answer`, `steps`, `tool_results` сохранён.

## Оптимизация и воспроизводимость

В локальном `.env` задано `OLLAMA_KEEP_ALIVE=60m` вместо прежних 10 минут. Это уменьшает вероятность повторной загрузки весов после паузы, но не ускоряет генерацию уже загруженной модели. Модель занимает память дольше. Значение по умолчанию в репозитории остаётся `10m`. Поведение описано в [Ollama FAQ](https://docs.ollama.com/faq).

Перед демонстрацией можно выполнить `python -m scripts.warm_ollama`: пустой запрос загружает модель без отправки источников. Предварительная загрузка переносит затраты на подготовку; первое вычисление всё ещё может быть медленным. Скрипт запускается явно и не блокирует обычный старт FastAPI. Он не скачивает модель.

`python -m scripts.benchmark_agent --source-id <ID> --repeat 3 --output logs/timing.json` выполняет последовательные запросы к работающему стенду и сохраняет длительности, число шагов, размер ответа и статусы инструментов. В отчёте нет текста вопроса/ответа и строк CSV. Ошибки учитываются отдельно. Первый запрос не помечается автоматически как холодный: это видно по `load_ms`. Повторы могут использовать prompt cache; медиана трёх запросов не является общей оценкой производительности всех вопросов. Корректность ответа нужно проверять отдельно.

Контекст 4096, лимит 768 токенов локальной Gemma и `THINKING=0` оставлены прежними. Инструменты не пропускаются, готовые ответы не подставляются. Следующие оптимизации следует сравнивать на одинаковых вопросах: фиксировать загрузку, обработку входа, число выходных токенов и качество результатов. Уменьшать контекст или обрезать ответ ради меньшей цифры без проверки качества нельзя.

При первом запросе также выполнялись тесты приложения; сравнительный аппаратный бенчмарк в полностью изолированной системе не проводился. Повторы используют кеш Ollama. На прогретых запросах основное время занимает генерация, а не чтение CSV. Удержание модели 60 минут направлено именно на устранение повторных загрузок во время работы со стендом.

Проверки изменения: 27 frontend-тестов, TypeScript/production build, 71 backend/browser-тест; два пропуска Windows (POSIX process groups и права symlink). Регрессионные тесты проверяют перевод наносекунд, отсутствующие метрики, накопление времени двух вызовов и инструмента, логирование сбоя без вопроса, таймер ожидания/ошибки/повтора, привязку позднего ответа к источнику и совместимость контрактов.
