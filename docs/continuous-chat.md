# Продолжение диалога в интерфейсе

Раньше каждый вопрос отправлялся в stateless `/agent/ask`, а интерфейс показывал только одну пару вопрос/ответ. Теперь первая отправка создаёт серверный чат через `POST /chats`; все последующие вопросы диалога идут в `/agent/chat?chat_id=...`. Предыдущие пользовательские вопросы и ответы ассистента передаются модели существующим backend. Новый агент и новая схема БД не требуются.

Справа показаны все сообщения выбранного диалога. История слева содержит диалоги, названные первым вопросом, а не отдельные вопросы. «Новый анализ» начинает новый диалог; серверная запись создаётся только при его первом вопросе. Старый диалог можно выбрать и продолжить. Кнопка «Результаты инструментов» у каждого ответа открывает именно его данные; время ответа остаётся у соответствующего сообщения.

Идентификаторы диалогов привязаны к источнику в состоянии текущей вкладки. Смена источника не переносит предыдущий контекст в другой чат. Поздний ответ сохраняется в своём диалоге и не переключает пользователя обратно. Одновременная повторная отправка в один диалог блокируется; отдельные диалоги могут обрабатываться параллельно. Создание чата завершается независимо от отмены ожидания, чтобы полученный ID можно было использовать при повторе. Ошибка модели не создаёт ещё один чат. Ответ с чужим `chat_id` отклоняется frontend-проверкой. Vite проксирует `/chats`, поэтому создание работает и в dev-режиме.

## Ограничения

Сервер хранит сообщения, но UI пока не восстанавливает список диалогов после обновления страницы и не загружает старую историю через пагинацию. Это часть будущей #18; текущая доработка решает продолжение диалога в открытой вкладке. Старые вопросы из предыдущей stateless-версии автоматически в контекст не переносятся.

Backend сохраняет пользовательский вопрос до обращения к модели. После ошибки или отмены повтор остаётся в том же чате, но может добавить ещё одно пользовательское сообщение: идемпотентности HTTP пока нет. Отмена ожидания не гарантирует прекращения генерации на сервере. Инструментальные результаты и метрики отображаются из ответов текущей вкладки, а в серверной истории сейчас сохраняются только вопросы и текстовые ответы. Длинная история ограничена контекстным окном модели (для локальной Gemma настроено 4096); семантическая память и сжатие контекста не добавлены.

## Проверка

Unit/component-тесты проверяют два вопроса в одном chat_id, новый анализ, возврат в прежний диалог, изоляцию источников, поздние ответы, повтор после ошибки, отмену создания без потери ID и отклонение чужого chat_id. Backend-тест подтверждает, что второй запрос получает предыдущую пару user/assistant, а новый чат начинает с пустого контекста. HTTP smoke проверяет `/chats` и продолжение диалога как через production FastAPI, так и через Vite proxy.

Frontend: 31 тест прошёл, TypeScript/production build успешны. Python: 71 тест прошёл в общем прогоне, два пропущены на Windows; browser acceptance сначала превысил пятисекундное ожидание загрузки UI при параллельной проверке Gemma, затем отдельно прошёл. Итог — 72 успешных Python-теста с учётом отдельного browser-прогона. Длинное название диалога не расширяет список истории; полное название доступно в title и доступной подписи кнопки.

Живая проверка Edge + Gemma `gemma4:12b`: первый вопрос просил запомнить синтетическую метку «маяк-4826» и ответить без повторения метки. Модель ответила «Принято.» за 16.3 с. На следующий вопрос без указания метки модель ответила «маяк-4826» за 3.6 с. Оба запроса использовали один chat_id; серверная история содержала четыре сообщения, UI — две пары сообщений и один пункт истории. Проверены «Новый анализ» и возврат в прежний диалог. Созданный проверкой серверный чат удалён после проверки; пользовательские чаты не затронуты. Скриншот находится только в игнорируемом `frontend/test-results/continuous-chat.png`.
