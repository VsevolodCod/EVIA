# #29: условия запроса в сохранённом дашборде

## Исправляемая проблема

Ранее `DashboardDraft` не представлял фильтры и календарную группировку.
При построении передавался пустой список условий, а невалидный ответ LLM
заменялся обзором по первым полям схемы. Поэтому панель могла выглядеть
успешной, не отвечая запросу «для A за 2025 год по кварталам».

## Поведение

- План модели обязательно содержит `filters` (пустой список означает весь
  источник). Поля проверяются по выбранной схеме, source_id назначает сервер.
  Условия соединяются через AND, список значений одного поля — через in/not_in.
- Период выражается обычными фильтрами даты: `gte 2025-01-01`,
  `lt 2026-01-01` включают весь 2025 год, в том числе последний день с временем.
- Карточка line принимает `time_grain`: day, week, month, quarter, year или
  null для группировки по исходным значениям. Группировать время можно только
  по типизированному date/datetime/timestamp, не по строковой подписи месяца.
  SQL DATE_TRUNC группирует по началу календарного интервала, сохраняя год.
  Неделя начинается в понедельник; заполнение отсутствующих периодов нулями
  не выполняется. Порядок — по значению даты.
- Условия сохраняются в `definition.filters` каждой карточки. Это относится
  и к дополнительному аргументу filters инструмента build_chart: повторное
  открытие не расширяет выборку. Во frontend паспорт показывает условия и шаг.
- После двух невалидных/оборванных планов возвращается clarification без
  создания артефактов. Модель может явно запросить уточнение (cards=[]).
  После ошибки вычисления нельзя перепланировать на «любую простую карточку»
  и выдавать её за ответ. Частичный результат явно содержит ошибки карточек.

Пример плана (для схемы event_day, amount, segment):

```json
{
  "title": "A за 2025 год",
  "filters": [
    {"field": "segment", "operator": "eq", "value": "A"},
    {"field": "event_day", "operator": "gte", "value": "2025-01-01"},
    {"field": "event_day", "operator": "lt", "value": "2026-01-01"}
  ],
  "cards": [
    {"type": "kpi", "title": "Итого", "field": "amount", "aggregate": "sum"},
    {"type": "line", "title": "По кварталам", "x": "event_day", "y": "amount",
     "aggregate": "sum", "time_grain": "quarter"}
  ],
  "clarification": null
}
```

## Проверки

`tests/test_dashboard_constraints.py` проходит реальную цепочку AgentRuntime →
CSV/DuckDB → сохранение → закрытие/открытие базы → повторный расчёт.
Модель заменена stub, вычисления — настоящие. Три схемы, включая кириллицу;
числовой эталон: KPI 145, кварталы 60/40/-5/50. Другой сегмент, соседние годы
и NULL-дата проверяют границы фильтров. Отдельно проверены все пять шагов
времени и сохранение ID 001 в дополнительном фильтре.

Отрицательные сценарии: отсутствующие filters, чужое поле, неверный оператор,
оборванный JSON, ошибочный тип фильтра, SQL вместо шага, отсутствие поля даты.
Frontend проверяет отображение реальных условий и группировки в паспорте.

Полные backend/frontend/browser проверки запускаются в GitHub Actions.
Локальное приложение, Ollama и тяжёлые тесты не запускаются.

## Границы приёмки

Это исправление условий и воспроизводимого пересчёта, не полное закрытие #29.
До закрытия нужна живая проверка Cloud.ru на новом SHA: две разные схемы и
неизвестная fixture, проверка каждой карточки, открытие панели через UI и
независимое ревью. Валидный JSON сам по себе не доказывает, что LLM правильно
поняла естественный язык; это проверяется отдельно живыми вопросами.

OR между разными полями, разные условия для разных карточек, fiscal calendar,
пользовательские часовые пояса и составные метрики не добавлены. Для них план
должен запрашивать уточнение, а не отбрасывать условие. Полная память диалога
относится к #17; версии метрик и снимки данных — к #19/#28. Пересчёт сохранённой
панели использует текущий источник, а не архивный снимок.
