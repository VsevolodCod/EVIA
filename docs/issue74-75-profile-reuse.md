# #74 / #75: повторное использование профиля и последовательные вопросы

База изменения: `main@2232ec7` (PR #83). Это частичное исправление двух открытых
инцидентов, а не подтверждение их полной приёмки на реальной модели.

## Причина и исправление

Обзор источника после #83 каждый раз пересчитывал полный профиль CSV. Интерфейс
запрашивал тот же профиль отдельно, поэтому повторные вопросы выполняли одинаковые
статистические сканы. Для непустого CSV с датой затем дополнительно выполнялись
COUNT/MIN/MAX, хотя результат уже был в полном профиле. Сбой этого лишнего SQL
мог превратить готовый обзор в ошибку.

Теперь SourceService переиспользует проверенный профиль неизменяемого CSV-снимка.
Ключ включает source ID, snapshot ID, версию схемы, версию парсера и размер выборки.
Кэш существует только в памяти экземпляра сервиса; после перезапуска рассчитывается
заново. Обновление кода не использует старый формат профиля с диска.

Лимиты — 32 записи и 16 MiB сериализованных значений. Вытесняется наименее недавно
использованная запись; слишком большой профиль возвращается, но не сохраняется.
Одновременные читатели одного ключа разделяют вычисление; разные ключи не держат
общий lock во время SQL. Ответы десериализуются отдельно: изменение выдачи вызывающим
кодом не меняет будущие ответы. Ошибки не кэшируются. Live PostgreSQL читается заново.
Семантика выборки и точных CSV-статистик не меняется.

Полный профиль даёт обзор без второго SQL и без LLM. В ответе остаются schema/profile
tool results; фиктивная таблица от несуществующего SQL не создаётся. При изменении
источника во время чтения сохраняется проверка версии и ограниченный повтор.
Для неполного профиля оставлен прежний SQL fallback.

Простые описательные вопросы с префиксами «А», «А теперь», «Теперь» используют те же
действия, что и вопросы без префикса. Условия и составные запросы не обрезаются:
сопоставляется весь оставшийся вопрос. Это не структурированная память диалога (#17)
и не замена уточнениям из отдельного PR #84.

## Проверки

Тяжёлые проверки запускаются в GitHub Actions; локально — только синтаксис и diff.
Никаких сетевых вызовов модели в добавленных тестах нет.

- `tests/test_profile_cache.py`: переиспользование, изоляция значений, лимиты
  записей/байтов, конкуренция, повтор после ошибки, новый импорт/схема/выборка,
  ошибочный импорт, неверный snapshot и отсутствие кэша для live PostgreSQL.
- `tests/test_csv_query_agent.py`: обзор с несколькими датами работает при
  недоступном SQL-пути; проверки гонок перенесены на актуальную границу чтения профиля.
- `tests/test_descriptive_actions.py`: разговорные префиксы; фильтры и составные
  запросы не превращаются в безусловный обзор.
- `tests/test_discovery_acceptance.py`: настоящий FastAPI, CSV с `;`, DuckDB,
  SQLite и семь вопросов в одном чате при недоступном inference. Проверяются точные
  факты, ведущие нули, сохранённые ответы, изоляция источников и отсутствие повторных
  profile scans после запроса профиля из UI.

Число сканов проверяется вместо нестабильного требования «тест быстрее N секунд».
Это доказательство устранения лишней работы, но не p50/p95 реальной Gemma.

## Что ещё нужно для закрытия issues

| Критерий | Состояние после изменения |
|---|---|
| Повторные сканы профиля одного снимка | Устранены в пределах лимитов кэша и одного процесса; проверяются в CI |
| Лишний SQL полного обзора | Убран; факт не зависит от марки модели |
| Последовательные базовые вопросы и сохранение | Добавлена CI-приёмка без inference; реальный стенд проверяется отдельно |
| Холодный/тёплый inference и полный корпус | Не проверены этим исправлением |
| Две модели, ≥30 тёплых измерений, p50/p95, бюджеты | Ещё нужны; вопросы без LLM учитывать отдельной категорией |
| Все десять продуктовых сценариев | Не входят целиком в #74/#75; остаются задачи контекста, дашбордов, связей и статистики |

Использовать `Refs #74, Refs #75`, а не автоматическое `Closes` до фактической приёмки.

## План реальной проверки без неожиданной нагрузки

Выделенного стенда сейчас нет. Ранее запретили тяжёлые локальные прогоны;
новый прогон запускается после явного согласования окна и нагрузки.
Не устанавливать и не загружать вторую модель автоматически.

1. После согласования проверить установленные теги и память, записать SHA,
   hardware/runtime, параметры и хеш датасета. Не публиковать исходные строки,
   секреты и веса. `gemma3:12b` и `gemma4:12b` — разные теги.
2. Сначала короткий smoke одной модели: семь вопросов из API-теста в одном чате,
   затем вопрос с настоящим планированием и заранее известным результатом.
   Отсутствие LLM на metadata-пути учитывать отдельно от скорости inference.
3. После успешного smoke согласовать бюджеты и расширить замеры: cold отдельно,
   ≥30 тёплых повторов, ошибки/таймауты и p50/p95 с размером выборки. Одинаковый
   протокол выполнить на базовом и исправленном коммите на одном железе.
4. Существующий `scripts.benchmark_local_models` сравнивает два установленных
   тега на versioned корпусе. Полный запуск может быть долгим; это не smoke.
   Шаблон для согласованного запуска ниже сейчас не выполнялся:

```powershell
.venv\Scripts\python -m scripts.benchmark_local_models MODEL_A MODEL_B --warm-repeats 30 --timeout 60 --max-tokens 512 --output ..\local-benchmark.json --markdown ..\local-benchmark.md
```

Результаты этого runner не покрывают автоматически всю последовательность чата.
Согласовать возможность прервать прогон; таймаут HTTP не гарантирует немедленной
остановки уже начатой генерации внутри Ollama.
