# Механизм повторных запросов к LLM

## Назначение

Механизм ретраев обеспечивает автоматический повтор запросов к языковой модели при временных ошибках провайдера или получении пустого ответа.

Он вынесен в отдельный модуль `app/llm/retry.py`, чтобы отделить обработку повторных запросов от основной логики агента.

Основные задачи:
- повторять запросы при временных сетевых и HTTP-ошибках;
- повторять запросы при получении пустого ответа;
- ограничивать количество попыток;
- увеличивать задержку между повторными попытками;
- не повторять запросы при ошибках, которые требуют изменения параметров или исправления запроса;
- позволять настраивать поведение через `.env`;
- обеспечивать независимое тестирование механизма.

## Структура

```text
app/
├── llm/
│   └── retry.py
├── config.py
└── agent.py

tests/
└── test_llm_retry.py
```

Ответственность компонентов:

| Компонент | Назначение |
|---|---|
| `retry.py` | Политика ретраев, определение повторяемых ошибок, выполнение повторных запросов |
| `config.py` | Чтение настроек ретраев из переменных окружения |
| `agent.py` | Использование механизма ретраев при обращении к LLM |
| `test_llm_retry.py` | Проверка поведения механизма ретраев |

## Настройки `.env`

```dotenv
AGENT_LLM_RETRY_MAX_ATTEMPTS=5
AGENT_LLM_RETRY_BASE_DELAY_SECONDS=0.5
AGENT_LLM_RETRY_BACKOFF_MULTIPLIER=2.0
AGENT_LLM_RETRY_MAX_DELAY_SECONDS=8.0
```

| Параметр | Значение по умолчанию | Описание |
|---|---:|---|
| `AGENT_LLM_RETRY_MAX_ATTEMPTS` | `5` | Максимальное количество попыток выполнить запрос, включая первую |
| `AGENT_LLM_RETRY_BASE_DELAY_SECONDS` | `0.5` | Начальная задержка перед повторным запросом, в секундах |
| `AGENT_LLM_RETRY_BACKOFF_MULTIPLIER` | `2.0` | Множитель увеличения задержки |
| `AGENT_LLM_RETRY_MAX_DELAY_SECONDS` | `8.0` | Максимальная задержка между попытками, в секундах |

**Количество попыток включает первоначальный запрос.** Например, `MAX_ATTEMPTS=5` означает один первоначальный запрос и максимум четыре повторных.

Настройки читаются при инициализации конфигурации приложения. Изменение `.env` не влияет на уже созданный объект политики ретраев до повторной загрузки конфигурации и пересоздания соответствующих объектов.

## Алгоритм работы

Для выполнения запроса используется функция `call_with_retry()`.

1. Выполняется первоначальный запрос к LLM.
2. Если запрос завершился успешно и ответ не требует повтора, результат возвращается вызывающему коду.
3. Если возникла повторяемая ошибка или получен ответ, который политика считает невалидным для текущей операции, проверяется лимит попыток.
4. Если попытки остались, вычисляется задержка и выполняется ожидание.
5. Запрос выполняется повторно.
6. Если лимит исчерпан, выбрасывается исходное исключение либо `LLMRetryExhausted` — в зависимости от причины повторов.

### Экспоненциальная задержка

Задержка перед очередной попыткой рассчитывается по формуле:

\[
d_n = \min(d_0 \cdot m^{n-1}, d_{\max}),
\]
($$
d_n = \min(d_0 \cdot m^{n-1}, d_{\max}),
$$)

где:
- \(d_n\) ($d_n$) — задержка перед повторной попыткой;
- \(d_0\) ($d_0$) — начальная задержка;
- \(m\) ($m$) — множитель увеличения;
- \(d_{\max}\) ($d_{\max}$) — максимальная задержка;
- \(n\) ($n$) — номер повтора, начиная с единицы.

*форматирование формул может не отображаться*

Например, при начальной задержке `0.5` секунды, множителе `2` и максимальной задержке `8` секунд последовательность будет следующей:

| Номер повтора | Задержка |
|---:|---:|
| 1 | 0.5 с |
| 2 | 1 с |
| 3 | 2 с |
| 4 | 4 с |
| 5 и далее | 8 с |

Фактическое количество повторов ограничивается параметром `AGENT_LLM_RETRY_MAX_ATTEMPTS`.

При нулевой начальной задержке повторы выполняются без ожидания.

## Повторяемые ошибки

Механизм классифицирует ошибки HTTP и сетевого взаимодействия.

### HTTP-ошибки

Повторяются следующие HTTP-статусы:

| Статус | Значение |
|---:|---|
| `408` | Request Timeout |
| `429` | Too Many Requests |
| `500` | Internal Server Error |
| `502` | Bad Gateway |
| `503` | Service Unavailable |
| `504` | Gateway Timeout |

### Сетевые ошибки

Повторяются исключения `httpx.TransportError`, включая ошибки соединения и транспортного уровня.

### Пустой ответ

Вызывающий код передаёт функцию `is_retryable_result`, определяющую, требует ли полученный результат повторного запроса.

Например, для ответа модели повтор может потребоваться, если:
- отсутствуют вызовы инструментов;
- содержимое ответа пустое или состоит из пробельных символов;
- причина завершения соответствует допустимым для повтора значениям.

Правила определения пустого ответа задаются вызывающим кодом, а не самой политикой ретраев. Поэтому механизм можно использовать для разных операций, не привязывая его к конкретному формату ответа LLM.

## Ошибки, которые не повторяются

Не любая ошибка должна приводить к повторному запросу.

В частности:
- HTTP `400` не входит в список повторяемых статусов;
- ошибки авторизации не повторяются, если их статус не включён в список повторяемых;
- произвольные исключения, не относящиеся к повторяемым сетевым ошибкам, пробрасываются вызывающему коду;
- результат, который не признан повторяемым через `is_retryable_result`, возвращается без дополнительного запроса.

Это позволяет избежать бессмысленных повторов, когда проблема не исчезнет сама по себе.

## Исключения

### `LLMRetryExhausted`

Используется, когда все попытки завершились получением результата, который вызывающий код признал непригодным для дальнейшей обработки.

Например, если каждый запрос возвращает пустой ответ, после исчерпания лимита попыток возникает `LLMRetryExhausted`.

### Исходные исключения

Если все попытки завершились повторяемой HTTP- или сетевой ошибкой, после последней попытки пробрасывается исходное исключение.

Это позволяет вызывающему коду различать ситуации, когда провайдер не отвечает, и ситуации, когда провайдер отвечает, но возвращает непригодный результат.

## Использование

Пример независимого использования механизма:

```python
response = await call_with_retry(
    operation=lambda: llm.chat(messages, tools),
    policy=retry_policy,
    is_retryable_result=lambda result: (
        not result.tool_calls
        and not (result.content or "").strip()
        and result.finish_reason in (None, "stop")
    ),
)
```

Здесь:
- `operation` — асинхронная операция, которую необходимо повторять;
- `policy` — объект `LLMRetryPolicy` с настройками ретраев;
- `is_retryable_result` — функция, определяющая, нужно ли повторять запрос на основании полученного результата.

Пример предполагает, что интерфейс ответа модели содержит поля `tool_calls`, `content` и `finish_reason`.

В агенте ошибки исчерпания попыток можно преобразовать в соответствующую ошибку выполнения агента, например `IncompleteModelOutput`.

## Взаимодействие с агентом

Ретраи LLM и лимит шагов агента решают разные задачи.

| Механизм | Что ограничивает |
|---|---|
| Ретраи LLM | Количество попыток выполнить один запрос к модели |
| Лимит шагов агента | Количество последовательных шагов рассуждения и выполнения инструментов |
| Обработка ошибок инструментов | Реакцию агента на ошибки при выполнении конкретного инструмента |

Если запрос к модели временно завершился ошибкой, механизм ретраев повторяет его в рамках текущего шага. Это не должно считаться новым шагом агента.

Если инструмент завершился ошибкой, результат обработки инструмента должен передаваться агенту в соответствии с существующей логикой выполнения. Сам механизм ретраев LLM не должен автоматически повторять выполнение инструмента.

При использовании нескольких уровней ретраев необходимо учитывать их суммарный эффект: например, если HTTP-клиент и агент оба повторяют один и тот же запрос, фактическое количество сетевых обращений может значительно превысить ожидаемое.

## Тестирование

Тесты расположены в `tests/test_llm_retry.py`.

Они не запускают агента и не отправляют реальные запросы к провайдеру. Для имитации поведения используются фиктивные ответы, `AsyncMock` и подмена `asyncio.sleep`.

Запуск:

```bash
python -m pytest tests/test_llm_retry.py -v
```

Проверяются следующие сценарии:

| Тестируемая ситуация | Ожидаемое поведение |
|---|---|
| Успешный первый запрос | Результат возвращается без повторов |
| HTTP `502`, затем успех | Выполняется повторный запрос |
| Пустой ответ, затем успех | Выполняется повторный запрос |
| Повторяемая HTTP-ошибка во всех попытках | После исчерпания лимита пробрасывается исходное исключение |
| Пустой ответ во всех попытках | Возникает `LLMRetryExhausted` |
| HTTP `400` | Исключение пробрасывается без повтора |
| Непредвиденное исключение | Исключение пробрасывается без повтора |
| Ошибка соединения, затем успех | Выполняется повторный запрос |
| Экспоненциальная задержка | Проверяется увеличение задержки и её ограничение |
| Нулевая задержка | Допускаются повторы без ожидания |
| Некорректная политика | Проверяется выбрасывание `ValueError` |

Ожидания `asyncio.sleep` подменяются асинхронным моком, поэтому тесты не тратят реальное время на ожидание.

## Ограничения и дальнейшее развитие

1. **`Retry-After`.** Для HTTP `429` и некоторых ответов `503` можно добавить обработку заголовка `Retry-After`, чтобы учитывать рекомендации провайдера по времени ожидания.
2. **Случайный разброс задержки (jitter).** При большом количестве параллельных запросов можно добавить случайную составляющую к задержке, чтобы избежать синхронных повторов.
3. **Логирование.** Полезно фиксировать номер попытки, тип ошибки и задержку, не записывая чувствительное содержимое запросов.
4. **Метрики.** При необходимости можно отдельно учитывать количество повторов, число исчерпанных политик и длительность каждого обращения к модели.
5. **Таймауты.** Ретраи не заменяют таймауты запросов. Каждый вызов LLM должен иметь ограничение по времени.
6. **Идемпотентность.** Повторять безопасно только операции, для которых повторный вызов не приводит к нежелательным побочным эффектам. Для обычного запроса генерации это обычно приемлемо, но для инструментов, изменяющих данные, необходима отдельная политика.

Таким образом, механизм ретраев отвечает только за повторное выполнение одной операции по заданным правилам. Решения о продолжении работы агента, повторном выполнении инструментов и обработке окончательных ошибок остаются за вызывающим кодом.
