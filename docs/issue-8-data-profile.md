# Паспорт набора данных (#8)

`Profile` описывает конкретный снимок источника, а не произвольную выборку из
текущей базы. Для локального CSV успешный импорт материализует неизменяемый
`snapshot_id`; профиль строится по этой материализации и возвращает тот же
`snapshot_id`.

## Семантика полного профиля CSV

`coverage: "full"` означает, что EVIA просканировала все строки
материализованного CSV-снимка. В таком ответе `processed_rows` — точное число
строк снимка и должно совпадать с `accepted_rows` отчёта его импорта.

Точные поля полного профиля:

- верхний уровень: `processed_rows`, `coverage`, `snapshot_id`;
- для каждого столбца: `non_null_count`, `null_count`, `empty_count`,
  `distinct_count`, `uniqueness_ratio`, `is_identifier_candidate`;
- для столбцов, безопасно приведённых к числу: `numeric.count`, `minimum`,
  `maximum`, `total`, `average`;
- для приведённых даты/времени: `temporal.count`, `minimum`, `maximum`.

`empty_count` — подмножество ненулевых значений: это пустая строка, а не SQL
`NULL`. `is_identifier_candidate` — техническая эвристика для этого снимка,
не подтверждение бизнес-ключа. Числовые и временные блоки отсутствуют, когда
столбец не имеет соответствующего безопасного типа.

Поля выборки всегда помечают ограниченную часть строк: `sample_size`,
`sample_limit`, `sample_non_null_count`, `sample_null_count`,
`distinct_sample_values`, `top_values` и `top_values_coverage: "sample"`.
Даже в полном CSV-профиле `top_values` считаются только по ограниченной
выборке, поэтому они не являются точной частотной статистикой всего снимка.
Контракт проверяет, что размер выборки не превышает лимит, а сумма заполненных
и пропущенных значений каждого столбца равна размеру этой выборки. Пустая
строка в live-выборке PostgreSQL учитывается как пропуск: её нельзя показать
пользователю как заполненное значение.

`coverage: "sample"` — другой вариант контракта `Profile`. Он содержит только
поля выборки и не имеет права заявлять `processed_rows`, `snapshot_id` или
точные счётчики столбцов. Так обозначаются ограниченные live-профили, например
для PostgreSQL.

## Недействительность снимка

Повторный успешный импорт CSV создаёт новый `snapshot_id`, новую
материализацию и новый полный профиль. Клиент должен сопоставлять паспорт,
результаты аналитики и отображаемую схему с их `snapshot_id`; паспорт прошлого
снимка нельзя показывать как паспорт новой версии файла. Неудачный повторный
импорт не меняет опубликованный снимок и его профиль. Профиль вычисляется по
материализованному снимку, поэтому для него нет отдельного кэша, который можно
переиспользовать после смены снимка.

## Воспроизводимая приемка девяти исходных CSV

Команда ниже импортирует каждый локальный CSV во временный каталог, строит
`Profile` и пишет только безопасную сводку: имя файла, SHA-256, сгенерированные
`source_id`/`snapshot_id`, принятые и обработанные строки, покрытие, длительность
и коды ошибок. Она не записывает строки CSV, заголовки, значения профиля,
тексты исключений или секреты.

```bash
python -m scripts.verify_csv_profiles '/path/to/прогон таски 5' \
  --output docs/issue-8-originals-profile-audit.json
```

По умолчанию команда требует ровно девять файлов `*.csv`. Она завершается с
ненулевым кодом, если число файлов отличается, импорт или профилирование
завершилось ошибкой, `processed_rows != accepted_import_rows` либо
`coverage != "full"` хотя бы для одного локального CSV. Для изолированного
синтетического запуска количество файлов можно явно задать через
`--expected-files`.

```bash
python -m pytest -q tests/test_verify_csv_profiles.py
python -m scripts.verify_csv_profiles '/Users/vsevolod/Desktop/program/Linza-BI/прогон таски 5' \
  --output docs/issue-8-originals-profile-audit.json
```

Проверка конкретного прогона сохранена в
[metadata-only audit](issue-8-originals-profile-audit.json). Повторный запуск
создаёт новые безопасные идентификаторы временных источников и снимков, но хеши
и точные счётчики должны совпасть, пока байты исходных файлов не менялись.
