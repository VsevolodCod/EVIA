# EVIA

Принятая в `main` поставка, участие в интеграции, функции, исправления и известные проблемы: [отчёт от 18 октября](docs/delivery-2026-10-18.md).

Локальное рабочее пространство для исследования CSV: источники и история слева, данные в центре, чат с помощником Эвией справа. Интерфейс подключён к FastAPI команды и показывает фактические ответы и результаты инструментов.

Итог локальной работы по #3, #4 и #16, проверенные коммиты и ограничения: [отчёт о проверках](docs/issues-3-4-16-verification.md).

## Быстрый запуск

Нужны **Python 3.11+** и **Node.js 22.12+ или 24+** с npm. Подготовка зависимостей требует сети; после подготовки интерфейс и mock-режим запускаются локально без скачиваний. Для Ollama заранее установите runtime и выбранную командой модель.

Из корня репозитория:

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
npm ci --prefix frontend
npm --prefix frontend run build
python scripts/run.py
```

Windows PowerShell (активация окружения не обязательна):

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
npm.cmd ci --prefix frontend
npm.cmd --prefix frontend run build
$env:LLM_PROVIDER = 'mock'
.venv\Scripts\python scripts/run.py
```

Для dev-режима: `.venv\Scripts\python scripts/run.py --dev`. Node.js и npm должны быть в PATH. В Windows launcher запускает Vite напрямую через Node, а `Ctrl+C` / `Ctrl+Break` останавливают принадлежащие ему процессы.

Откройте **http://127.0.0.1:8000**. API-документация: **http://127.0.0.1:8000/docs**. `Ctrl+C` завершает процессы, созданные launcher. Готовое приложение обслуживается одним FastAPI; Node.js нужен для подготовки сборки, а не для её дальнейшего запуска.

## Публикация на Railway

Railway разворачивает EVIA как один контейнер: на стадии сборки Docker собирает React, а FastAPI отдаёт готовый интерфейс и API с одного домена. Первый production-запуск использует тестовый провайдер, поэтому не требует GPU, Ollama или ключа внешней LLM.

1. В проекте Railway откройте сервис **EVIA** → **Settings** → **Source** и выберите репозиторий `VsevolodCod/EVIA`, ветку `main`. Root Directory оставьте пустым.
2. Railway обнаружит `Dockerfile`. В **Deploy** оставьте пустыми Pre-deploy Command и Custom Start Command: команды уже определены образом.
3. Добавьте Volume к сервису EVIA с Mount Path `/data`.
4. В **Variables** задайте:

   ```dotenv
   LLM_PROVIDER=mock
   BI_DATA_DIR=/data
   CATALOG_DB_PATH=/data/catalog.db
   CHAT_DB_PATH=/data/chats.db
   ```

   `PORT` Railway задаёт сам. Не добавляйте `DATABASE_URL`: текущая версия приложения хранит каталог, файлы и историю в SQLite на Volume. Сервис Postgres можно оставить созданным, но его подключение требует отдельной миграции приложения.
5. В **Networking** включите HTTP Proxy и сгенерируйте публичный домен. В **Healthcheck Path** укажите `/health`.
6. Нажмите Deploy. Успешная проверка: домен открывает интерфейс, а `<домен>/health` отвечает JSON с `status: "ok"`.

Перед отправкой в Railway можно проверить тот же production-образ локально:

```sh
docker build -t evia:local .
docker run --rm -p 8000:8000 -e PORT=8000 -v "$(pwd)/.local-data:/data" evia:local
```

Откройте `http://127.0.0.1:8000/health`. Второй запуск с тем же `-v "$(pwd)/.local-data:/data"` использует те же CSV, каталог и сохранённые чаты. Каталог `.local-data/` содержит пользовательские данные и не должен попадать в git.

### Первое исследование

1. Загрузите `sample-data/sales.csv` — это небольшой синтетический пример, не конкурсные данные.
2. Выберите источник. Посмотрите строки, схему и профиль. Идентификаторы `0001` и `0002` должны сохранить ведущие нули.
3. Задайте вопрос, например «Что есть в данных?». Выбранный `source_id` передаётся агенту.
4. Ответ поддерживает Markdown, списки, таблицы и блоки кода. Результаты инструментов отображаются отдельно от предпросмотра исходного CSV.
5. Задавайте уточняющие вопросы в том же диалоге: модель получает предыдущие сообщения. «Новый анализ» начинает отдельный диалог; слева можно вернуться к прежнему. Сообщения сохраняются в backend, но список диалогов интерфейса пока хранится в текущей вкладке и очищается при перезагрузке.

При `LLM_PROVIDER=mock` показан демонстрационный режим: он проверяет интеграцию и возвращает тестовый ответ, **не выполняет аналитический SQL**. Поведение mock-провайдера унаследовано от команды: первый запрос вызывает `list_sources`, следующие могут вернуть только текст.

## Разработка

После установки зависимостей, из активированной `.venv`:

```sh
python scripts/run.py --dev
```

Откройте **http://127.0.0.1:5173**. Launcher запускает FastAPI на 8000 и Vite на 5173. Vite проксирует `/health`, `/sources`, `/agent` и `/chats` к API; CORS и отдельный публичный API не нужны. Изменения frontend обновляются автоматически. После изменения Python перезапустите launcher.

Другие порты:

```sh
python scripts/run.py --dev --port 8100 --ui-port 5200
```

Порты должны быть свободны и различаться. Для запуска Vite отдельно задайте `BI_API_TARGET` (по умолчанию `http://127.0.0.1:8000`). Launcher устанавливает его автоматически. Параметр `--host` по умолчанию ограничивает доступ локальной машиной. Авторизация и многопользовательская изоляция в этом прототипе не реализованы; это локальный инструмент.

## Локальная модель и данные

При необходимости скопируйте `.env.example` в `.env`. Основные настройки:

| Переменная | Назначение |
| --- | --- |
| `LLM_PROVIDER` | `mock` по умолчанию; `ollama` для локальной модели |
| `LLM_MODEL` | Точное имя уже установленной модели из `ollama list` |
| `OLLAMA_BASE_URL` | По умолчанию `http://127.0.0.1:11434` |
| `OLLAMA_KEEP_ALIVE` | Как долго Ollama держит модель в памяти после запроса; по умолчанию `10m` |
| `TIMEOUT` | Таймаут провайдера модели в секундах |
| `AGENT_MAX_STEPS` | Ограничение числа шагов агента |
| `BI_DATA_DIR` | Каталог исходных CSV (по умолчанию `data/`) |
| `CATALOG_DB_PATH` | SQLite-каталог источников (по умолчанию `BI_DATA_DIR/catalog.db`) |
| `BI_CATALOG_DB` | Прежнее имя настройки каталога; используется, если не задан `CATALOG_DB_PATH` |
| `CHAT_DB_PATH` | База серверных диалогов (по умолчанию `BI_DATA_DIR/chats.db`) |

Для уже установленной локальной модели запустите Ollama и сохраните в игнорируемом `.env` (точный тег проверьте через `ollama list`):

```dotenv
LLM_PROVIDER=ollama
LLM_MODEL=qwen2.5-coder:7b
OLLAMA_BASE_URL=http://127.0.0.1:11434
OLLAMA_KEEP_ALIVE=10m
THINKING=0
TIMEOUT=120
MAX_TOKENS_G=256
AGENT_MAX_STEPS=5
```

Если ранее в PowerShell задан `$env:LLM_PROVIDER='mock'`, удалите эту переменную (`Remove-Item Env:LLM_PROVIDER -ErrorAction SilentlyContinue`) либо поменяйте её на `ollama`: переменные процесса имеют приоритет над `.env`. Перезапустите `scripts/run.py` и обновите страницу. Проверить наличие модели можно через `http://127.0.0.1:11434/api/tags`, выбранного провайдера — через `/health`. Health приложения не подтверждает готовность модели: первый запрос может долго загружать веса и прогревать Ollama.

`TIMEOUT` действует на один вызов модели, `MAX_TOKENS_G` ограничивает его генерацию. Провайдер использует контекст 4096 токенов. В примере модель остаётся в памяти 10 минут после запроса; это занимает RAM/VRAM, но уменьшает число холодных запусков во время тестирования. Для выбранного CSV настоящий провайдер сначала генерирует структурированный SQL по схеме, затем `query_data` вычисляет ответ. Числа ответа строятся из `QueryResult`; пустая выборка не подменяется выдуманными значениями. Ошибочный SQL допускает одно исправление. Политика SQL описана в [docs/safe-sql-executor.md](docs/safe-sql-executor.md), сравнение локальных моделей — в [docs/local-llm-evaluation-2026-10-20.md](docs/local-llm-evaluation-2026-10-20.md).

Проверены реальные вызовы схемы и предпросмотра через Gemma, в том числе отображение ответа в Edge: [локальный отчёт Ollama](docs/ollama-local-verification.md).

В чате отображаются прошедшее ожидание и итоговое время ответа. В «Подробности времени» доступны серверные измерения модели и инструментов. Для отдельной предварительной загрузки весов выполните `.venv\Scripts\python -m scripts.warm_ollama`. Для серии замеров: `.venv\Scripts\python -m scripts.benchmark_agent --source-id <ID> --repeat 3 --output logs/timing.json`. Запросы реально вызывают модель и используют выбранный источник. [Как читать метрики и сравнивать скорость](docs/response-timing.md).

Для существующего каталога укажите его путь явно. Иначе новый путь по умолчанию создаст пустой каталог, не перемещая прежние данные. Каталог автоматически создаёт таблицы при первом запуске; зависимости `SQLAlchemy[asyncio]` и `aiosqlite` перечислены в `requirements.txt`.

CSV и каталог сохраняются backend на локальном диске. Browser storage используется только для настройки тихого режима, не для файлов, вопросов или ответов. Не коммитьте `.env`, `data/`, веса моделей, конкурсные CSV и логи. Шрифты системные, пакеты входят в сборку; frontend не использует CDN, облачные сервисы или телеметрию.

Эвия показывает состояние выполняемого запроса. Тихий режим и системная настройка `prefers-reduced-motion` отключают движение. Показ этапов не имитирует внутренний прогресс модели. Кнопка остановки прекращает ожидание ответа в браузере; API пока не гарантирует отмену вычисления на сервере.

## API-контракт интерфейса

Версионируемые схемы, примеры для A/B/C и правила совместимости: [contracts/README.md](contracts/README.md). Документ разделяет работающий legacy API и целевой контракт следующих задач; `QueryResult` выдаётся инструментом `query_data`, отдельного SQL HTTP API нет.

| Метод и путь | Запрос / результат |
| --- | --- |
| `GET /health` | `{status, llm_provider}` |
| `GET /sources` | `DataSource[]`: `source_id`, `name`, `source_type`, `status`, `created_at`, `schema_version` |
| `POST /sources/csv` | multipart `file`, необязательное `name`; возвращает `DataSource` |
| `GET /sources/{id}/schema` | `SourceSchema` с `objects[].fields`, `row_count`, `relations` |
| `GET /sources/{id}/preview?limit=100` | Массив строк; допустимый limit 1–100 |
| `GET /sources/{id}/profile` | `sample_size`, `sample_limit`, `columns`, `note` |
| `POST /agent/ask` | `{question, source_ids: [id]}` → `AgentResponse`: `answer`, `request_id`, `status`, `answer_kind` (`demo`, `model`, `computed`), `analysis.sql`, `results`, `tool_results`, `timing` |
| `POST /chats` | `{title}` → `{chat_id, title, created_at, updated_at}`; создаётся перед первым вопросом диалога |
| `POST /agent/chat?chat_id=...` | `{question, source_ids: [id]}` → ответ с `chat_id` и `timing`; продолжает диалог |

Элемент `tool_results`: `{tool_name, ok, data, error}`. `data` может быть массивом строк, объектом или скаляром; UI не трактует любой результат как выполненный SQL. Ошибка инструмента сохраняется видимой даже при наличии текстового ответа. Схема даёт точное число строк; статистика профиля рассчитана на ограниченной выборке (сейчас до 500 строк).

Интерфейс использует `/agent/chat` с одним `chat_id` на диалог. Backend передаёт предыдущие пользовательские вопросы и ответы ассистента в контекст модели. «Новый анализ» создаёт отдельный контекст, смена источника переключает его диалоги. Справа отображается вся переписка выбранного диалога; кнопка результатов у каждого ответа открывает именно его результаты. `/agent/ask` сохранён для самостоятельных запросов и benchmark-скрипта.

Хранилище серверных чатов исправлено в [#16](docs/issue-16-persistent-chat.md). UI теперь продолжает серверные диалоги, но восстановление списка после перезагрузки, пагинация истории и управление сохранёнными сессиями ещё относятся к #18. Локальная привязка источника сохраняется в текущей вкладке; она не является серверной авторизацией или изоляцией пользователей. При сбое LLM вопрос уже может быть записан: повтор использует тот же чат, но HTTP-идемпотентность пока не реализована. Подробности: [продолжение диалога](docs/continuous-chat.md).

## Проверки

```sh
npm --prefix frontend test
npm --prefix frontend run build
python -m pytest -q
```

Frontend: типы, сборка и тесты интерфейса/контрактов, Markdown и изоляции состояния. Backend: исходные тесты команды, реальный FastAPI-сценарий загрузки → схема → предпросмотр → профиль → агент, отдача статических ресурсов и launcher. Тесты используют временные каталоги и синтетические данные.

Перед PR также проверяется живой запуск через HTTP. Browser-проверка макета зависит от наличия подключённого браузера; её отсутствие указывается в отчёте, а не считается успешной проверкой.

Дополнительная браузерная приёмка (Playwright, отдельная установка):

```powershell
.venv\Scripts\python -m pip install -r requirements-browser.txt
$env:BI_BROWSER_TESTS = '1'
$env:BI_BROWSER_CHANNEL = 'msedge'
.venv\Scripts\python -m pytest tests/browser -q
```

`msedge` использует установленный Edge; для Chrome задайте `chrome`. Для поставляемого Playwright Chromium выполните `python -m playwright install chromium` и оставьте `BI_BROWSER_CHANNEL` незаданным. В shell POSIX: `BI_BROWSER_TESTS=1 BI_BROWSER_CHANNEL=msedge python -m pytest tests/browser -q`. Тест сам поднимает изолированный FastAPI в mock-режиме, проверяет клавиатуру и ширину 390 px. Снимки записываются в игнорируемый `frontend/test-results/`. Без `BI_BROWSER_TESTS=1` этот тест пропускается. В Windows отдельно пропускаются POSIX-тест групп процессов и symlink-тест при отсутствии соответствующих прав.

## Текущие ограничения и ответственность

- CSV-парсер поддерживает **UTF-8/BOM, запятую, `;`, табуляцию и `|`**. Уже загруженные схемы обновляются автоматически. [Границы исправления #7](docs/csv-delimiter-fix.md): прочие кодировки и raw/typed-импорт ещё требуют Data Engine.
- SQL-исполнитель, DuckDB и полный Text-to-SQL — зависимости от участников A/B. В этой задаче нет самостоятельно вычисленных UI-агрегатов, выдуманных графиков или готовых ответов по конкурсным данным.
- Сохранённые дашборды, восстановление списка серверных сессий после перезагрузки, PostgreSQL-коннектор, авторизация и масштабирование относятся к следующим задачам.
- Профилирование и загрузка в текущем backend синхронные. Ограничения больших файлов и конкурентных запросов нужно закрыть до многопользовательского развёртывания.

Интеграция объединяет `issue-1-fullstack-workspace` (`26ea8c8`) и актуальную `tes/pipeline_1` (`a27cefe`), продолжение исходной базы `929b8dd`. PR направляется в `tes/pipeline_1`, автоматического слияния нет. [Отчёт об интеграции и проверках](docs/integration-2026-10-17.md).

## Маскот EVIA: 40 состояний

Используется предоставленный автором `EVIA_mascot_integration_pack`: все 40 прозрачных SVG сохранены без изменений в `frontend/public/mascot/`. Это упрощённая векторная версия дизайна, а не 3D-модель. Типизированный каталог: `frontend/src/features/mascot/states.ts`, компонент: `frontend/src/components/EviaMascot.tsx`.

```tsx
<EviaMascot state="welcome" size={128} />
<EviaMascot state="analyzing" size={96} decorative quiet />
```

Галерея: **http://127.0.0.1:8000/?mascot=1** (замените порт на выбранный при запуске). Все состояния можно выбирать вручную, сравнивать размеры 64–256 px и отключать движение. Карточки галереи статичны; анимируется только выбранный персонаж. Галерея не запускает API-запросов и не меняет рабочие данные.

В рабочем пространстве загрузка CSV включает `uploading`, успешная загрузка — `uploaded`, ошибки формата — `invalid_csv`, ввод вопроса — `listening`, ожидание агента — `thinking`, повтор — `retrying`, полученный ответ — `explaining`, ошибки инструментов — `warning`. Прекращение ожидания — `cancelled`; серверная обработка при этом может продолжаться. Ошибки сети, доступа и таймаута определяются по типу ошибки/HTTP-статусу. Загрузка метаданных сопровождается `profiling`, пустая таблица — `empty_table`. Состояние запроса остаётся привязано к своему источнику.

У API нет событий отдельных этапов агента. Поэтому `analyzing`, `validating`, `calculating`, графики, дашборды, экспорт и прочие дополнительные состояния доступны компоненту и галерее, но не включаются по вымышленному таймеру или догадке из текста LLM. Mock не считается признаком локального LLM и не включает `offline`.

Анимация — мягкое появление и парение всего SVG. Независимая анимация глаз и рук, 3D и скелетная анимация не входят в этот набор. `quiet`, тихий режим приложения и `prefers-reduced-motion` отключают движение. Рядом с маскотом в чате всегда есть текстовый статус; самостоятельный компонент имеет русское альтернативное описание, `decorative` отключает дублирующее озвучивание.

После обновления из worktree пересоберите frontend и перезапустите launcher:

```sh
npm --prefix frontend run build
.venv/bin/python scripts/run.py --port 8100
```

### Визуальная доработка перед слиянием

Согласно актуальной #3, единое название продукта и помощника — EVIA. Стартовый экран содержит загрузку CSV и чат. Mock обозначен меткой «Тестовая модель» в шапке. Подробности памяти и истории доступны в «О чате». Кнопки имеют различимые disabled/focus-состояния; системное уменьшение движения сохраняется. Генерируемый `frontend/dist` обновляется командой сборки, исходники находятся в `frontend/src`.

## Прямой PostgreSQL-источник

Для подключения allowlisted таблиц PostgreSQL без CSV задайте `POSTGRES_DSN` и
`POSTGRES_ALLOWED_TABLES`. EVIA выполняет операции в новых read-only транзакциях
с timeout и ограничениями результата. Настройка Railway, минимальные права роли
и локальная интеграционная проверка описаны в [docs/postgresql-source.md](docs/postgresql-source.md).
